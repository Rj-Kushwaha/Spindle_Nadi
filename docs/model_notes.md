# Model behavior and limitations

## Synthetic dataset

The checked-in dataset is generated with a fixed seed and contains ten
simulated machines at different workloads and spindle-speed setpoints. Each machine has twelve healthy
samples followed by gradual degradation until its simulated degradation
reaches 1.0. The five scripted fault modes are distributed across the machines.
Sensor noise and operating time are included. Labels come from the simulator,
not independently observed machine failures.

## Feature engineering

For each sensor reading, workload- and commanded-speed-adjusted excess is
calculated relative to the simulator's healthy equations:

- Temperature: subtract `38 + 0.20 × workload + (rpm_setpoint − 1800) × 0.0012`
- Vibration: subtract `0.75 + 0.006 × workload + (rpm_setpoint − 1800) × 0.00008`
- Motor current: subtract `4 + 0.075 × workload + (rpm_setpoint − 1800) × 0.0003`
- RPM drop: normalize setpoint deviation to an equivalent 1800 RPM scale
- X/Y/Z vibration, spindle-load and torque excess, bearing-temperature excess,
  coolant-flow drop, coolant-temperature excess, lubrication-pressure drop,
  acoustic excess, feed-rate drop, estimated tool wear, and estimated power are
  calculated against simulator baselines conditioned on workload and/or
  commanded RPM.

Recent five-reading means, five-reading slopes, and rolling RPM standard
deviation add context. A machine's history is kept separate when calculating
rolling features.

## Models and evaluation

Isolation Forest is fitted only to healthy training features. The UI shows a
lower-tail score scaled against the healthy training-score distribution and
whether Isolation Forest classifies the reading as an outlier.

Random Forest regression estimates the simulator degradation fraction from
sensor features. Evaluation holds out entire machine IDs (rather than randomly
splitting neighboring time-series samples), then reports MAE and warning-class
precision, recall, F1, and confusion matrix. The dashboard calculates these
from the generated data at model startup. They measure performance on this
synthetic simulator distribution only; they do not represent real-world
accuracy.

The health-state thresholds are risk below 0.50 = NORMAL, risk at least 0.50
and below 0.85 = WARNING, and risk at least 0.85 = CRITICAL. Thus the
50–64% interval is WARNING. These are prototype operating settings, not
engineering alarm limits.

The injected bearing-wear, cooling-degradation, lubrication-loss, tool-wear,
and spindle-imbalance modes create different synthetic sensor signatures.
They are scenario labels, not independently validated fault diagnoses. Tool
wear and power are estimates generated by the simulator, not direct sensor
measurements.

## Explanations and RUL

The explanation is an estimate: for each input feature, the model prediction
is repeated with that one feature replaced by its healthy training median.
Positive reductions are shown as contributions. This is a small, model-based
counterfactual, not a causal explanation.

RUL extrapolates the model's degradation estimate using the simulator schedule
(0.06 degradation per 0.1 simulated operating hour). It is a demonstration of
the interface and calculation only. It is not a probability distribution,
failure guarantee, or validated estimate of a physical machine's lifetime.

The displayed 0–100 health score is `100 × (1 − estimated risk)`, rounded to
an integer. It is a relabeled inverse of model risk, not a separate measurement
or validated physical-health metric. Sensor-quality checks compare the latest
simulated sample with broad illustrative plausibility ranges and flag stale
timestamps after 30 seconds. These checks identify data-quality concerns; they
do not diagnose equipment failures.

The fixed-limit comparator uses illustrative temperature, vibration, current,
and RPM thresholds displayed in the Evidence tab. It must not be used as a
safety limit. The application computes warning lead time only from a machine
trace where both events (model warning and fixed-limit crossing) have already
been observed. It does not extrapolate lead time or claim that the model leads
the limit in advance.

## What-if, service simulation, and digital twin-style view

Workload/RPM what-if results compare two cloned simulator instances advanced
with paired random state, one at current settings and one at alternate workload
and commanded spindle speed. Both simulator sensor generation and feature
baselines account for RPM. The live simulator is unchanged. Operating-point
adjusted features intentionally allow expected raw readings to rise without
treating that response alone as degradation.

Downloadable maintenance reports summarize the current synthetic sample,
model evidence, risk trend, sensor data-quality findings, fixed-limit
comparison, prototype recommendation, and recorded alert and maintenance
history. Report output is a prototype record, not an industrial work order.

Virtual maintenance reduces the simulator's scalar degradation by the
operator-selected recovery fraction, preserves accumulated operating time,
records before and after model estimates, and advances up to ten samples to
verify whether status returns to NORMAL. A lower risk without a NORMAL state is
only partial improvement, not recovery. The virtual scalar repair is
illustrative, not a component-level physical repair model.

The digital-twin-style view is a conceptual schematic that colors component
markers using local feature contributions. It has no CAD geometry, calibrated
physics, or actuator integration. The maintenance copilot uses deterministic
templates grounded in the local model output; it does not call an LLM or issue
validated industrial instructions.

## Before real deployment

Use validated sensor instrumentation and historical runs with verified
maintenance/failure labels; assess sensor drift, missing readings, workload
and machine differences; define safety thresholds with equipment experts; test
out-of-distribution and false-alarm behavior; and independently validate any
maintenance decision process. This prototype does none of those validations.

The recorded-data replay accepts CSV, whitespace-delimited TXT, Excel
workbooks, and ZIP archives containing those data formats for visualization
only. Timestamp columns are preserved and sorted; known cycle fields are used
as replay time in their original units; otherwise, a synthetic one-second per
row replay axis is labeled as synthetic. Headerless 26-column C-MAPSS text
files are recognized as engine ID, cycle, three operating settings, and
generic `sensor_1` through `sensor_21` channels. Unknown channel names are
preserved; user mappings affect display labels only and must be supported by a
dataset codebook. No benchmark upload is passed to the CNC model or assigned a
failure-risk score. PDF references are kept separate and are not interpreted as
sensor data. The parser does not silently fill missing values. Actual telemetry
requires a read-only, site-approved connection
to a machine controller or gateway and an agreed tag/unit mapping; this project
does not include hardware, protocol credentials, or a physical-machine link.

The ESP32 USB viewer accepts newline-delimited JSON containing calibrated
temperature, vibration, current, or RPM channels. Those physical readings are
kept separate from the generated training data and do not receive the synthetic
model's risk score. Calibration and a representative labeled dataset are
prerequisites for making physical-machine model claims.
